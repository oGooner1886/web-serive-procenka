# Архитектура и функциональные возможности Web-сервиса «Проценка»

> **SPA** для подбора автозапчастей и проценки по каталогам поставщика «Фаворит-Моторс».  
> Стек: **React 18**, **Redux Toolkit**, **Axios**, **Bootstrap 5**, **Vite 5**, **i18next**.

---

## 1. Обзор ключевых функциональных возможностей (Features)

1. **Двухэтапный сценарий проценки автозапчастей <br> (согласно регламенту API «Фаворит-Моторс»)**:
   * **Этап 1 (Поиск брендов)**: <br> Пользователь вводит каталожный номер детали (например: `OP570`). Выполняется запрос к API без указания бренда. Приложение получает список товаров, парсит и выводит уникальные карточки производителей.
   * **Этап 2 (Проценка по выбранному бренду)**: <br> При клике на конкретного производителя отправляется целевой запрос с параметрами `number`, `brand` и `analogues=on`. Таблица с предложениями отображается строго после явного выбора бренда.
2. **Интеллектуальная защита от спама и гонок запросов**:
   * **Debounce 500 мс** на поле ввода: <br>пользователь печатает артикул, запрос отправляется автоматически только после паузы в наборе текста.
   * **Cooldown 1000 мс и блокировка спам-кликов** на кнопке «Найти»:<br> при нажатии Enter или кнопки поиск запускается мгновенно (`leading: true`), а повторные клики блокируются на 1 секунду.
   * **Отмена предыдущих незавершенных HTTP-запросов (AbortController)**: <br>при быстром изменении артикула или переключении между брендами незавершенный сетевой запрос немедленно отменяется через встроенный `signal`, защищая интерфейс от эффекта гонки (Race Condition).
3. **Двухуровневое кэширование (In-Memory LRU Cache)**:<br>
   * Кэш ответов первого этапа (бренды) и второго этапа (предложения со складов) с временем жизни **TTL = 5 минут** и лимитом в 100 записей.
   * Повторный поиск по тому же артикулу или повторный выбор бренда открывается мгновенно без повторного сетевого вызова.
4. **Безопасность и санитарная обработка данных (Defense in Depth)**:
   * Очистка пользовательского ввода от скрытых null-байтов (`\x00`), непечатных управляющих символов ASCII/Unicode (`0x00-0x1F`, `0x7F-0x9F`), обрезка краевых пробелов и ограничение длины строки (защита от DoS / ReDoS).
   * Безопасная сериализация параметров URL через `encodeURIComponent` в Axios.
   * Безопасное хранение ключей авторизации API в `.env` файле без хардкода в репозитории.
5. **Мультиязычность (i18n) + Интеллектуальный перевод номенклатуры запчастей**:
   * Полноценная локализация интерфейса (Русский / Английский) на базе `i18next`, `react-i18next` и `i18next-browser-languagedetector` с сохранением выбора пользователя в `localStorage`.
   * Специализированный модуль автоперевода автозапчастей (`partTranslator.js`): переводит специфические термины из базы 1С («Фильтр масляный» $\rightarrow$ «Oil filter», «Колодки тормозные» $\rightarrow$ «Brake pads», «Рычаг подвески» $\rightarrow$ «Suspension control arm») и модификаторы положения («передний/задний», «левый/правый» $\rightarrow$ «front/rear», «LH/RH») с сохранением оригинального названия во всплывающей подсказке.
6. **Трехуровневая адаптивная верстка (3-Tier Responsive Layout)**:
   * **Мобильные устройства (< 768px)**: пропорциональный компактный хедер, плиточная сетка выбора брендов, трансформация таблицы предложений в удобные мобильные карточки со складами и ценами (Card-view).
   * **Лаптопы и планшеты (768px – 1199px)**: промежуточные гармоничные размеры шрифтов и сетки.
   * **Десктоп / Мониторы ($\ge$ 1200px)**: полноразмерная таблица предложений с фиксированным распределением колонок и поддержкой бейджей («Запрошенный» / «Аналог»).

## 2. Архитектура Redux Toolkit: Slice и Store

### 2.1. Почему выбран Redux Toolkit вместо локального состояния (`useState`)

В приложении такого класса использование глобального хранилища через Redux Toolkit обеспечивает ключевые преимущества:

* **Полное разделение логики и представления (Separation of Concerns)**:
  Вся бизнес-логика (санитизация, проверка кэша, формирование параметров, выполнение запросов, парсинг товаров и уникализация брендов, отмена запросов) инкапсулирована внутри `partsSlice.js`. Компоненты интерфейса остаются "тонкими" и декларативными, отвечая исключительно за отображение.
* **Предсказуемый однонаправленный поток данных (Unidirectional Data Flow)**:
  Любое изменение состояния происходит строго через детерминированные экшены (`setSearchQuery`, `setSelectedBrand`, `clearAll`, жизненный цикл thunk: `pending` / `fulfilled` / `rejected`). Это исключает несинхронность данных между формой поиска, блоком брендов и таблицей предложений.
* **Масштабируемость корпоративного уровня**:
  При добавлении нового функционала (корзина заказов, история запросов, фильтрация по складам, экспорт в Excel/PDF, авторизация дилера) архитектура легко расширяется новыми слайсами без переписывания существующего дерева компонентов.
* **Инструменты отладки (Redux DevTools)**:
  Возможность покадровой инспекции каждого состояния, просмотр точного payload экшенов и аудит производительности в dev-режиме (`devTools: import.meta.env.DEV`).

### 2.2. Структура состояния (State Shape)

Начальное состояние в `partsSlice.js` спроектировано минималистично и нормализовано:

```javascript
const initialState = {
  searchQuery: '',       // Актуальный артикул для поиска
  brands: [],            // Массив уникальных брендов для Этапа 1
  selectedBrand: null,   // Выбранный бренд для запуска Этапа 2
  rawGoods: [],          // Сырой массив предложений и аналогов из API
  brandsLoading: false,  // Индикатор загрузки брендов (Этап 1)
  brandsError: null,     // Текст ошибки для Этапа 1
  offersLoading: false,  // Индикатор загрузки предложений со складов (Этап 2)
  offersError: null,     // Текст ошибки для Этапа 2
};
```

#### Почему именно такое разделение:
1. **Независимые флаги загрузки и ошибок**:
   `brandsLoading` и `offersLoading`, а также `brandsError` и `offersError` разделены. Это позволяет пользователю видеть, на каком конкретно шаге находится процесс, не сбрасывая UI первого этапа при ошибке загрузки второго.
2. **Сброс зависимых состояний при новом поиске**:
   При вызове `fetchBrands.pending` автоматически очищаются старый `selectedBrand`, `rawGoods` и предыдущие ошибки. Таблица второго этапа гарантированно скрывается до явного выбора бренда, строго отвечая бизнес-требованию ТЗ.
3. **Хранение `rawGoods` в Redux вместо преобразованного массива**:
   В Redux State сохраняется исходный ответ сервера (`rawGoods`), а преобразование в плоский список строк таблицы (`flattenGoodsToOffers`) вынесено в мемоизированный селектор (`useMemo`) в компоненте `OffersTable`. Это экономит память Redux Store и исключает повторную сериализацию тяжелых объектов в сторе.

### 2.3. Асинхронные Thunk'и и отмена запросов (`AbortController`)

Каждый асинхронный процесс реализован через `createAsyncThunk`:

1. **`fetchBrands(number)`**:
   * Выполняет санитизацию артикула.
   * Проверяет наличие готового результата в `apiCache`.
   * При промахе кэша делает `GET /api` с передачей `{ number, signal }`.
   * Фильтрует заглушки API вида `{"goods": [{}]}`.
   * Выделяет список уникальных брендов через `Set` без дубликатов.
   * Сохраняет результат в `apiCache` и возвращает массив брендов.

2. **`fetchOffers({ number, brand })`**:
   * Проверяет кэш по составному ключу `NUMBER__BRAND`.
   * При промахе кэша делает `GET /api` с `{ number, brand, analogues: 'on', signal }`.
   * Сохраняет результат в кэш и возвращает товары.

3. **Защита от Race Condition**:
   В `App.jsx` ссылки на активные dispatch-промисы сохраняются в `useRef`:
   ```javascript
   if (activeBrandsPromiseRef.current) {
     activeBrandsPromiseRef.current.abort();
   }
   activeBrandsPromiseRef.current = dispatch(fetchBrands(query));
   ```
   Если пользователь быстро меняет ввод или переключает бренды, предыдущий запрос немедленно прерывается на уровне браузерного сетевого стека, а редюсер перехватывает сигнал отмены:
   ```javascript
   if (error.name === 'CanceledError' || error.name === 'AbortError') {
     return rejectWithValue('__ABORTED__');
   }
   ```
   Это гарантирует, что устаревший ответ никогда не перезапишет более свежие данные.

### 2.4. Мемоизация и оптимизация рендеринга (Performance)

* Все ключевые компоненты (`Header`, `LanguageSwitcher`, `SearchForm`, `BrandList`, `BrandButton`, `OffersTable`, `OfferTableRow`) обернуты в **`React.memo`**.
* Обработчики событий в `App.jsx` (`handleSearch`, `handleClear`, `handleSelectBrand`) стабилизированы через **`useCallback`**.
* Фильтрация предложений по поисковой строке и наличию на складе внутри таблицы вычисляется через **`useMemo`**, срабатывая только при реальном изменении входных зависимостей.

## 3. Рекомендации по дальнейшему развитию (Roadmap & Improvements)

1. **Виртуализация строк таблицы при больших объемах (> 500 позиций)**:
   При работе с популярными автозапчастями (например, фильтр VAG или колодки Toyota) API может возвращать сотни аналогов и складских предложений. Для сохранения 60 FPS на бюджетных мобильных устройствах рекомендуется подключить `@tanstack/react-virtual` для оконного рендеринга видимых строк таблицы.
2. **Экспорт результатов проценки**:
   Добавление функционала экспорта таблицы предложений в Excel (`.xlsx`) или печать коммерческого предложения для клиента в PDF.
3. **Корзина и оформление заказа**:
   Добавление слайса `cartSlice` с сохранением выбранных позиций, подсчетом итоговой суммы и возможностью формирования заявки поставщику.
4. **Комплексное тестирование**:
   * Unit-тесты для утилит (`partTranslator.test.js`, `offerTransformers.test.js`, `sanitize.test.js`, `cache.test.js`) на Vitest.
   * Интеграционные тесты для Redux thunk'ов (`partsSlice.test.js`) с моками через `msw` (Mock Service Worker).
   * E2E-тесты критического пользовательского пути (ввод артикула $\rightarrow$ выбор бренда $\rightarrow$ проверка таблицы предложений) на Playwright.
5. **PWA (Progressive Web App) & Offline Mode**:
   Настройка Service Worker через `vite-plugin-pwa` для возможности автономного просмотра ранее закэшированных каталожных номеров при нестабильной связи на складе или в автосервисе.
